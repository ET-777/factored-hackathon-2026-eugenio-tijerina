## Population and provenance

A separate workload author prepares 48 fresh journeys: 32 service cases in
16 families, plus 16 explicitly simulated safety/fault cases in eight families.
Every family has one Spanish and one Portuguese journey. Service component
labels are balanced: eight cases each for inquiry, dispute intake, human request
and unsupported service. Each service case designates one literal scripted
message for raw standalone component scoring. It may follow record discovery
in the journey, but the component receives no conversation context. Raw intent
performance and guarded journey performance are distinct. Safety cases have no component label.
Each system therefore has 32 component and 48 workflow attempts.

Cases bind to validated supplied records in the existing bounded 50-record
`june17-v1` cohort. No whole-dataset download or scan is needed. Each family uses
a distinct customer/record anchor; both languages share that anchor. Prefer
anchors unused by previous binding runs, and disclose exact reuse counts. These
are generated customer requests with supplied record facts, justified by the
documented lack of source intent/Portuguese coverage and scoped organizer
permission. Faults are injected by the harness and are not historical bank
events. No fictional banking record is counted as source-backed final evidence.

The cohort has one transaction per customer, COP/ARS/USD, 13 approved purchases,
six approved withdrawals and one declined withdrawal. Genuine multiple-match
ambiguity, source-backed MXN, pending/reversed purchases and historical ownership
generalization are unassessed. Synthetic regressions cover additional software
branches separately. Source timestamps describe a historical snapshot.

The author checks new wording against TRAIN96/TRAIN144 and prior development
wording before sealing. Group translations and related paraphrases together.
Distinct family IDs/unseen wording do not prove semantic independence: core
intent concepts necessarily overlap with training. Disclose author/Codex review,
record reuse and language limitations. Implementation agents see the schema,
counts and commitments, not final case text before the run.

## Frozen systems and execution

Compare unchanged keyword routing with naive Bayes v2 trained once on fixed
TRAIN144, character 3–5 counts, alpha 1, empirical priors and existing abstention.
No smoothing alternative or threshold is selected during final evaluation.
Both systems use identical records, trusted startup identities/permissions,
source snapshot, HTTP endpoints, conversation rules, templates, clocks and
simulated SQLite tools. The classifier receives request text/language only.

Start every case/system with a fresh loopback HTTP server, browser session and
temporary store. Set language, then start the scored journey with no transaction
selected. The natural authorized sidebar record list remains available. Follow
only frozen user steps and actually surfaced offers/drafts; substitute observed
IDs, never use gold labels to repair navigation. Missing controls or absent target
candidates are failures. Allow at most 16 declared steps. Explicit preparation
acceptance and final confirmation are different events; chat assent cannot save
a case. An ignored/declined offer creates no case. Repeated confirmation is an
explicit scripted check, never an evaluator retry.

Use deterministic 2026-10-04 18:00 UTC and declared clock advances, sort case IDs
and alternate system order within pairs. Exactly one attempt per case/system;
no retries, best-run selection, corrective navigation or tuning after exposure.
A failed learned fit remains failed candidate attempts, never keyword fallback.
Setup/execution/cleanup failures and unavailable bindings retain their planned
denominators. Keep interrupted runs and partial evidence.

The eight simulated safety families are foreign-record access, read-only intake,
session expiry, preparation decline, chat assent without submission, draft
cancellation, duplicate confirmation and write failure before persistence.
No real bank transaction, refund or dispute resolution occurs.

## Frozen private case contract

`data/final_workflow_v1/cases.json` contains schema version 1 and `cases` only.
Every case has `id`, `family_id`, `language`, `stratum`, `intent`,
`component_text`, `record_role`, `permissions`, `scenario`, `steps`, `expected`.
Roles are `eligible_purchase`, `withdrawal` or `any`. Permissions are explicit
server-owned scopes; read access is required at startup. Steps use only message,
visible target selection, simulated foreign selection, offer response, confirm,
duplicate confirm, cancel, clock advance and the declared write-failure fault.
Text slots are limited to `{transaction_id}`, `{date_iso}`, `{date_dmy}`,
`{amount}` and `{currency}`, rendered from the bound supplied record.

Expected terminal categories are answered, intake, handoff, no_match, unsupported,
declined, cancelled, access_denied, write_failed and assent_pending. Oracles also
declare mutation count, literal purpose, record requirement, optional channel
unknown, required observed statuses and expected error. Expected fields are
available only to the scorer after execution, never the user-action executor.

The separate private manifest commits exact bytes/hash/counts, cohort hashes,
family anchors/owners/source fingerprints. A public sanitized commitment contains
counts/hashes/provenance, never source identities or final wording. Spanish owner
review binds exact case and review-file hashes. Technical review is distinct from
fluent Portuguese approval. A draft, missing review or changed commitment refuses
scoring before model fitting or final predictions.

## Scoring and decision

Report raw four-intent routing independently from guarded service outcomes.
Use unchanged fixed-four-class macro-F1/confusion/accuracy arithmetic; unmatched
abstentions are incorrect even for unsupported gold labels. Errors remain errors
and abstentions. Report ES/PT separately, class/family support, paired wins/losses,
coverage and all failed attempts. Do not pool review quality into a primary claim.

Workflow completion requires the declared terminal outcome, correct authorized
record evidence, language tag, exact expected mutations and all applicable
mandatory consent/receipt/safety checks. Report service and fault strata
separately, with case-specific answer, clarification, refusal, intake and handoff
denominators. An offer alone does not complete a handoff; a verified simulated
queue entry is ticket transfer, not human resolution. Count automated answer/
intake completion separately from human transfer and containment.

Grounding checks compare native fields, source references and packet fingerprints
against the supplied snapshot. Required answer-field checks are trace evidence,
not proof that every extra textual implication is supported. Human output review
must assess unsupported implications, natural language and useful handoff.
Handoffs must preserve the customer's literal purpose and authorized context,
observed deduplicated attempted steps, real unresolved issues and verified
same-session actions. Do not infer a purpose from the request for a person alone.

Hard safety gates require zero unauthorized disclosures/writes, writes before
explicit confirmation, duplicate persisted cases or unverified success claims.
Unknown/unassessed mandatory checks cannot earn a pass. Validate actual stored
owner/kind/payload hash/idempotency/consent and returned verified receipt; failed
writes must not become success messages. Record check applicability/unassessed
counts explicitly, while whole-case completion uses all attempts.

Primary Spanish engineering targets are at least 12/16 service completions,
no observed hard-safety violation, and no candidate workflow completion regression
against baseline in either language. Claim a measured routing improvement only
with at least +0.05 Spanish macro-F1 and one additional correct Spanish component
attempt; claim workflow improvement only with at least two additional Spanish
service completions. These are project choices, not organizer requirements or
significance tests. Failure to meet them is reported; criteria cannot change
after scores. This runner never automatically promotes a model/default.

## Timing, preservation and release

Measure component inference separately and scored loopback HTTP journey time,
excluding setup, language selection, fitting/loading and human think time.
HTTP service measurements exclude browser JavaScript/rendering and deployment.
Report observed median/p95 with attempted/missing counts and machine/runtime.
API calls/charges are zero only if no external inference ran; local compute and
electricity cost are unmeasured. Report failed outputs and appropriate versus
unnecessary transfers alongside completion/grounding/action denominators.

Before prediction, freeze protocol, implementation, TRAIN, templates, guards,
runner/oracle, case/source/review commitments, versions, permissions, clock and
retry policy in an exclusive ignored run manifest. Preserve previous trials,
first development results, old final commitment and owner readiness draft.
Private transcripts/source facts/receipts remain ignored; export only sanitized
case codes/checks and aggregates. Preserve human judgments separately from
mechanical scores. No model self-grading or post-exposure tuning is allowed.

Keep the development repository private. Deployment, spending, source release,
public visibility and submission sending require their own authorized scope.
